Suggestions

Suggestion llmbeans/hardware/detector.py:134 Broken shell interpolation in Python string literal

The Linux SSD detection path at line 134 uses $(mountpoint -d / | cut -d'/' -f3) inside a Python f-string path. This is shell syntax that will never be interpreted — it's passed literally to open() as a filesystem path, which will always fail, causing the function to fall through to the block-device loop. The code "works" because of the fallback, but the primary detection path is dead code.

Use subprocess.run(["mountpoint", "-d", "/"], ...) to get the mountpoint ID, then extract the device name, rather than embedding shell interpolation in a Python string.
Suggestion llmbeans/hardware/profiles.py:41–72 load_profiles() called repeatedly without caching

load_profiles() opens and parses a 1131-line JSON file on every call. It's called by get_profiles_by_category, get_profile_by_id, get_categories, match_profile_for_detection (which iterates all profiles), and indirectly by lookup_specs_for_detection. In the CLI flow, this means the JSON is parsed 5+ times during a single run. The data is static and small — caching would be trivial.

Add functools.lru_cache or a module-level singleton to cache the parsed profiles after first load.
Suggestion llmbeans/hardware/estimator.py:79 Magic constant — overhead_gb = 1.5

The OS + runtime overhead is hardcoded as 1.5 GB. This varies significantly by platform (macOS uses more RAM than a minimal Linux server) and by tool (llama.cpp vs vLLM have very different overhead profiles).

Extract to a named constant DEFAULT_OS_OVERHEAD_GB = 1.5 with a docstring, or make it configurable per hosting tool.

The inference efficiency factor of 0.6 (60% effective bandwidth) is hardcoded with a comment but not named. This is a significant tuning parameter that affects all performance estimates.

Suggestion llmbeans/recommenders/tools/mlx.py:36–37 Fragile model reference construction for GGUF models

When the model is GGUF format, the code constructs f"mlx-community/{model.name}" as the model reference. This assumes the model name matches the HF community repo naming convention, which is often not the case (e.g., a local file named Llama-3-8B-Q4_K_M.gguf would produce mlx-community/Llama-3-8B-Q4_K_M which likely doesn't exist).

Add a warning or fallback when constructing synthetic HF repo names from local filenames. Consider requiring the user to provide an explicit HF repo ID for MLX.
Suggestion llmbeans/hardware/profiles.py:189–190 Incomplete Apple Silicon RAM type detection

The RAM type inference for Apple Silicon only checks for "m4" and "m3" in the GPU name. M1 and M2 Macs (still widely used) would fall through to "LPDDR5", but M1 Macs use LPDDR4X. The 2024 MacBook Air (M3) uses LPDDR5, not LPDDR5X.

Expand the detection to cover M1 (LPDDR4X), M2 (LPDDR5), M3 (LPDDR5), M4 (LPDDR5X), or use the matched profile's ram_type as the primary source instead of inferring from chip name.
